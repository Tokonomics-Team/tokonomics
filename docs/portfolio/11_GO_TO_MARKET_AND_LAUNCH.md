# Go-to-Market and Launch Plan

## Launch thesis

Do not launch Tokonomics as a universal token or dollar saver. Launch a narrow, evidence-backed beta for developers with large multi-file or long agentic workflows.

## Initial ideal customer profile

- Uses AI coding tools daily.
- Works in medium/large repositories.
- Has metered usage, premium-request limits, context pressure or an enterprise governance need.
- Can evaluate complete task outcomes.
- Accepts an explicit VS Code participant or validated sidebar workflow.
- Values safe no-op behavior.

## Positioning

### Category

AI coding context assurance and efficiency.

### Positioning statement

For developers and AI platform teams running large-context coding workflows, Tokonomics reduces unnecessary context while preserving exact task evidence and showing what is measured versus estimated. Unlike generic prompt compressors, it rejects savings that lower task success.

### Message hierarchy

1. Complete tasks with less unnecessary context.
2. Preserve exact code evidence and fail safely.
3. Understand context and usage status.
4. Control workspace access with four simple settings.

### Messages to avoid

- “Save 80% on every prompt.”
- “Guaranteed no quality loss.”
- “Reduce every developer's bill.”
- “Intercepts Claude, Codex or Copilot automatically.”
- “State-of-the-art learned compression.”

## Packaging hypothesis

### Individual beta

- Free.
- Explicit participant and safe dashboard.
- Local trust controls.
- No commercial savings guarantee.

### Team/enterprise hypothesis

- Policy administration.
- Evidence and version governance.
- Aggregate content-free usage outcomes.
- Approved usage/billing integration where legitimately supported.
- Security and deployment controls.

Pricing requires willingness-to-pay research and production outcome evidence.

## Launch stages

### Stage 0 — Internal dogfood

Population: project owner and consenting technical reviewers.

Gate:

- known three-task quality regression resolved;
- full tests and installed VSIX pass;
- dashboard evidence labels correct;
- issue/feedback mechanism ready.

### Stage 1 — Design-partner alpha

Population: 5–10 carefully selected developers/teams.

Purpose:

- validate workflow and problem severity;
- collect task-level outcome evidence;
- diagnose missing context;
- test onboarding and privacy comprehension.

No public savings claim.

### Stage 2 — Closed beta

Population: 25–100 developers in validated segments.

Gate:

- workload-specific non-inferiority passed;
- missing-context recovery below threshold;
- at least one validated capacity/cost outcome;
- support burden acceptable.

### Stage 3 — Public beta

Population: self-selected VS Code users.

Gate:

- narrow external promise backed by evidence;
- public privacy/security materials;
- rollback and kill switch;
- onboarding and support content;
- product telemetry opt-in reviewed.

### Stage 4 — General availability

Gate:

- retention and repeat value;
- production quality guardrails stable;
- evidence refresh process operating;
- enterprise readiness for any paid offer.

## Launch scorecard

| Dimension | Metric | Beta gate |
|---|---|---|
| Quality | Workload task-success difference | Within pre-registered non-inferiority margin |
| Efficiency | Net completed-task resource reduction | ≥10% in promoted target workload |
| Recovery | Missing-context recovery rate | <2% attributable to Tokonomics |
| Activation | Install to first successful task | Target established after alpha |
| Retention | Second task within seven days | ≥80% among activated design partners target |
| Trust | Correct evidence/privacy comprehension | ≥90% critical concepts |
| Reliability | Successful send or actionable failure | ≥99.9% target |
| Security | Critical/high unresolved findings | 0 |
| Support | Severe issues per active user | Threshold established in alpha |

Targets marked as hypotheses require alpha calibration.

## Channel plan

- Public portfolio case study and technical product narrative.
- VS Code Marketplace only after launch gates.
- Developer communities focused on AI coding and FinOps.
- Design partnerships with platform/developer-productivity teams.
- Demonstration video showing pass-through, retrieval, fallback and unavailable cost—not just a savings animation.

## Content plan

### Before beta

- problem and philosophy article;
- privacy/data-flow explainer;
- benchmark methodology;
- “why we rejected an 83.9% headline” case study;
- getting-started guide.

### During beta

- evidence updates by workload;
- known limitations;
- release notes without architecture disclosure;
- user stories only with consent and measured outcomes.

## Sales/enterprise discovery questions

- How is AI coding usage billed or constrained?
- Which workflows dominate spend or quota?
- Can task outcomes be measured without collecting source?
- What deployment, privacy and procurement controls are required?
- Who owns developer-tool adoption and budget?
- What minimum result justifies a paid deployment?

## Launch risks and mitigations

| Risk | Mitigation |
|---|---|
| Users expect lower subscription price | Separate fixed-seat capacity messaging from metered cost |
| Native tools outperform Tokonomics | Comparative cohort and stop rule |
| Quality regression recurs | Per-workload gates, fallback and kill switches |
| Dashboard overstates benefit | Evidence labels and claim review |
| Extension workflow reduces adoption | Keep participant; validate sidebar before promotion |
| Architecture leaks through marketing | Public disclosure review and VSIX allowlist |

## Rollback plan

- Pause distribution.
- Disable affected internal capability.
- Keep previous validated VSIX.
- Preserve user settings where safe.
- Communicate affected version, symptom and workaround.
- Do not delete or modify user workspaces during rollback.

## Launch decision document

The launch review must answer:

1. Which customer and workload are we launching for?
2. What outcome is proven?
3. What is explicitly not claimed?
4. Did task quality meet its margin?
5. Are cost/capacity metrics complete?
6. What can be disabled or rolled back?
7. Are privacy, security, support and accessibility ready?
8. Who makes the human release decision?
